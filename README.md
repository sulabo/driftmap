# Ontology — 프로젝트 지식이 서로 다른 말을 하는 지점을 찾는 스킬

Claude Code 스킬입니다. 프로젝트 안에서 **결정 기록·코드·문서가 어긋난 곳**을
개념 단위로 찾아내고, 그 지도를 git으로 신선하게 유지합니다.

## 왜 만들었나

어떤 프로젝트에서 공략 문서가 옛 규칙을 말한다고 판정한 적이 있습니다.
그런데 코드를 열어 보니 **문서가 맞았습니다.**

어긋난 것은 문서가 아니라 **결정과 구현 사이**였습니다. 바꾸기로 정해 놓고
아직 코드에 넣지 않은 상태였죠. 문서끼리만 비교하면 이걸 "낡은 문서"로 오판하고,
멀쩡한 문서를 고쳐서 **없는 동작을 설명하게 됩니다.**

이 스킬의 모든 절차는 그 오판을 막기 위해 설계됐습니다.

## 무엇을 하나

프로젝트의 핵심 개념 8~12개를 골라, 각각을 네 면으로 봅니다.

| 면 | 무엇인가 | 어디서 찾나 |
|---|---|---|
| 정해진 것 | 결정 기록에 남은 것 | `DECISIONS.md`, `AGENTS.md` |
| 실제 동작 | 코드·테스트가 보여주는 사실 | 소스, 테스트 출력 |
| 설명된 곳 | 이 개념을 설명하는 문서들 | README, 스펙, 가이드 |
| 어긋남 | 위 셋 사이의 불일치와 그 종류 | 대조 결과 |

이 넷이 갈라지는 지점이 곧 문제입니다. 그리고 **어긋남의 종류마다 대응이 다릅니다.**

| 종류 | 뜻 | 대응 |
|---|---|---|
| 미구현 | 정했는데 코드가 아직 없음 | 문서를 고치면 안 된다 |
| 낡은 문서 | 코드가 바뀌었는데 문서가 옛말 | 문서를 고친다 |
| 미결 | 정해진 게 없음 | 결정이 필요하다는 신호 |
| 중복 정본 | 원본이 두 곳인데 우열 미정 | 어느 쪽이 이기는지 정한다 |

결과물은 프로젝트 안의 `CONCEPTS.md` 하나입니다. 새 파일을 만들지 않습니다.

## 핵심 아이디어: 낡음을 계산한다

지도가 낡는 건 시간이 흘러서가 아니라 **걸린 파일이 움직여서**입니다.
그러니 계산할 수 있습니다.

개념마다 "언제 어느 커밋 기준으로 확인했다"를 한 줄로 적어 둡니다.

```
- **메타**: 상태=미구현 · 확인=2026-09-07(`a1b2c3d`) · 파일=`src/game/levels.ts` · 이웃=개념 2(전제)
```

그러면 `git log <해시>..HEAD -- <파일들>`로 그 이후 커밋이 있었는지만 보면 됩니다.
**없으면 그 개념은 아예 열지 않습니다.** 개념 10개를 매번 전수 재확인할 필요가 없어집니다.

## 설치

```bash
git clone https://github.com/sulabo/ontology-skill.git ~/.claude/skills/ontology
chmod +x ~/.claude/skills/ontology/*.sh
```

Claude Code에서 "온톨로지 점검", "개념 지도 만들어줘", "신선도 점검"이라고 하면 발동합니다.

## 쓰는 법 — 네 가지 모드

| 모드 | 언제 | 비용 |
|---|---|---|
| 최초 생성 | `CONCEPTS.md`가 없을 때 | 큼 |
| 검진 | 지금 상태만 알고 싶을 때. 파일은 안 건드림 | 중간 |
| 갱신 | 어긋난 걸 고칠 때 | 중간 |
| **신선도 점검** | **평소. 기본 진입점** | 거의 없음 |

평소에는 신선도 점검만 돌리고, 재확인 대상이 0이면 거기서 끝냅니다.

### 스크립트 두 개

```bash
# 어느 개념이 재확인 대상인지 계산
./fresh.sh <CONCEPTS.md 경로> [저장소 루트]

# 지도 자체가 성한지 검사
./check.sh <CONCEPTS.md 경로>
```

`fresh.sh`의 판정은 여섯 가지입니다.

| 판정 | 뜻 |
|---|---|
| 신선 | 확인 이후 커밋 없음. 열지 않는다 |
| 재확인 필요 — 커밋 N건 | 파일이 움직였다 |
| 재확인 필요 — 기준 없음 | 확인 시점이 안 적혀 있다 |
| 재확인 필요 — 기준 소실 | 해시가 rebase로 사라졌다 |
| 재확인 필요 — 경로 소실 | 파일이 없다 |
| 재확인 필요 — 미추적 | 중첩 저장소다 |

`check.sh`는 다섯 가지를 봅니다. 요약표와 본문의 일대일 대응, 근거 경로가 계산에
쓸 수 있는 형태인지, 개념 간 참조가 양방향인지, 상태 어휘가 정해진 집합 안인지,
메타 줄이 있는지입니다.

## 이 스킬이 제일 경계하는 것

**조용한 거짓말입니다.**

`git log`는 경로가 틀려도, 그 저장소가 추적하지 않는 파일이어도 **오류 없이 빈 출력**을 냅니다.
그러면 파일이 사라진 개념이 "신선"으로 보고됩니다. 가장 급히 봐야 할 것이 가장 안전해 보이죠.

그래서 신선도를 계산하기 전에 경로 존재와 추적 여부를 먼저 확인합니다.
실제로 이 방어가 없었다면, 어떤 프로젝트에서 별도 git 저장소 안의 파일 네 개가
영원히 "신선"으로 보고될 뻔했습니다.

같은 이유로 **0건이 나왔을 때 "없음"이라고 단정하지 않습니다.**
형식이 안 맞아 못 셌을 수 있습니다. 실제로 어떤 저장소에서 `DECISIONS.md`가 표 형식이라
새 결정 22건을 1건으로 세고 있었습니다.

## 한계 (정직하게)

- 신선도는 **파일 단위**로만 계산합니다. 같은 파일의 무관한 줄이 바뀌어도 재확인 대상이 됩니다.
- **커밋된 이력만** 봅니다. 작업 트리의 미커밋 변경은 안 잡힙니다.
- 첫 실행은 개념마다 메타 줄을 채워야 해서 비용이 큽니다.
- 프로젝트 간 관계 추적은 설계만 있고 켜지 않았습니다.
